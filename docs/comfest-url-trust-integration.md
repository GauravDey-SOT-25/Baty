# Comfest URL Trust prototype integration

## Source and scope

The supplied archive `Comfest - 26-20261017T034440Z-1-001.zip` was reviewed from its existing extraction at `/Users/gauravdey/Documents/Codex/AI Model/Comfest - 26/`. Its separate `.git` history and the original extracted folder are preserved. No archive code was run, no contract was compiled or deployed, and no public URL or reputation provider was contacted during integration.

The usable workflow is now part of the existing Cyber Desk app under **URL Trust**. It supports a passive local domain lookup, a private user-maintained registry, explicit TLS certificate observation, and explicit optional domain-root reputation checks. Existing passive URL syntax analysis remains separate and does not resolve URLs.

## Integration behavior

- Passive domain lookup normalizes to a hostname and SHA-256 digest and checks the local registry only. Path, query, and fragment do not enter the local record key.
- Local records store the hostname, digest, certificate fingerprint, optional user note, timestamps, active/revoked state, and revocation note. Persistence uses atomic replacement and owner-only permissions on POSIX. Entries are limited to 1,000 and the JSON data file is Git-ignored.
- TLS inspection requires the in-app checkbox. It resolves the hostname, rejects non-global DNS answers, connects to the checked address directly on port 443, validates the certificate, and reads only the certificate from a TLS handshake. It issues no HTTP request and follows no redirects. Fingerprints are observations; a valid certificate does not establish site legitimacy.
- Reputation checks require a separate checkbox and a locally configured service key. The app sends only `https://<normalized-domain>/`, not the submitted path or query. No key is bundled or sent to the browser. Missing keys produce `not_configured`; provider failures are not treated as clean results.
- No blockchain is connected. Registry entries do not represent independent attestations, validator quorum, economic stake, Merkle anchoring, IPFS, or EIP-712 signatures.

## Configuration and privacy

Set `GOOGLE_SAFE_BROWSING_API_KEY` and/or `VIRUSTOTAL_API_KEY` in the ignored, owner-only `.env` file if you choose to use those providers. The keys remain server-side. Reputation checks can consume provider quota and disclose the selected domain root. TLS inspection performs a DNS lookup and a direct TLS handshake. Both are optional and require an in-app selection each time. No live provider check was performed while integrating this feature.

## Limits

This is a local prototype for human investigation. The local ledger is not tamper-proof or shared across machines. DNS answers can change after observation, certificate rotation is normal, reputation databases are incomplete, and no result proves safety. This workflow does not provide blockchain trust, multi-oracle consensus, ownership verification, site-content scanning, or production incident response.
